# Архитектура и решения

## Границы реализации

Один Vite/React/TypeScript проект и PostgreSQL в Supabase. Авторизация email/password через Supabase Auth; сервер Express/Nest не нужен. Используются Ant Design и React Router. Нет регистрации, администрирования ролей, вложений, уведомлений, аналитики, Realtime, Redux или фиктивных данных.

Пять страниц загружаются через React.lazy и динамические импорты. Suspense показывает индикатор загрузки; при переходах между рабочими страницами шапка приложения сохраняется. Пути и функции построения URL хранятся в общем объекте `routes` в `src/constants/routes.ts`; ссылки, редиректы и объявления маршрутов используют его.

Роли и статусы определены строковыми enum `UserRole` и `TaskStatus` в `src/types/domain.ts`. Они используются в типах базы, проверках интерфейса, фильтрах, подписях и цветах. Значения совпадают с PostgreSQL enum, поэтому преобразования при запросах не нужны. UUID конкретных участников остаются обычными данными, а не значениями enum. Проверки интерфейса не заменяют авторизацию в базе.

Миграции рассчитаны на свежий Supabase-проект и применяются по порядку: `001` создаёт схему и основные RPC, `002` настраивает защищённое каскадное удаление, `003` задаёт HTTP 409 (`PT409`) для конфликта устаревшей версии. Прикладной конфликт не должен обозначаться повторяемой ошибкой сериализации транзакции (`40001`). Для другой существующей схемы требуется отдельное сопоставление таблиц, ограничений и функций.

## Авторизация и целостность

- `profiles.role` — единственный источник ролей. Пользователь не может менять профиль через API. Администратор создаёт профили вручную, публичную регистрацию нужно отключить в Auth.
- Все четыре таблицы имеют RLS. API получает SELECT, но не INSERT, UPDATE, DELETE, TRUNCATE или управление триггерами/последовательностью. Отсутствуют write-политики. У `anon` нет доступа к данным и RPC.
- Схема `private` не должна входить в exposed schemas. `caller_role()` возвращает роль текущего пользователя и используется в RLS без рекурсии. Вспомогательные функции мутаций нельзя вызвать от `authenticated`.
- SECURITY DEFINER функции имеют `search_path = ''`, квалифицируют прикладные объекты схемами и проверяют пользователя внутри. Владелец обходит RLS, поэтому RPC явно проверяют роль и назначение. EXECUTE для PUBLIC отозван; API разрешён только для конкретных RPC.
- Постановщики читают профили для справочника исполнителей. Исполнители читают только свой профиль. `task_identities(task_id)` проверяет доступ и возвращает только UUID/имена автора, исполнителя и участников истории этой задачи; email не выдаётся.
- Составной FK `(assignee_id, assignee_role) → profiles(id, role)` и фиксированное `assignee_role = worker` запрещают назначение постановщика даже при конкурентном административном изменении роли. Автор берётся из `auth.uid()`, даты — из базы; триггер защищает ID, автора и дату создания от переписывания.
- Названия проверяются на наличие непробельного символа. Адрес и описание необязательны. Лимиты: имя пользователя 120, название объекта/задачи 200, адрес 500, описание 10000, комментарий 2000 символов.

## Статусы и конкурентная работа

Создание записывает `NULL → new`. Исполнитель может выполнить только `new → in_progress`, `revision → in_progress`, `in_progress → in_review` для своей задачи. Постановщик — только `in_review → accepted` или `in_review → revision`. Для доработки нужен непробельный комментарий. Принятый статус конечный. Постановщик не может выполнять переходы исполнителя.

`change_task_status` блокирует строку FOR UPDATE, проверяет актуальную роль, назначение, версию и допустимость перехода. Триггер повторно проверяет переход и записывает историю в той же транзакции. Локальная настройка `app.status_comment` передаёт лишь текст комментария из RPC в триггер, **не даёт разрешения** на запись. Она сбрасывается после операции и не используется для разрешения удаления. Ошибка откатывает статус и историю вместе.

Изменения и удаления существующих записей используют исходное `updated_at` как условие актуальности. Два вызова с одной версией не могут успешно изменить одну задачу дважды: второй получает STALE_DATA либо отсутствие записи. Редактирование содержания не принимает статус, автора или даты. Блокировки родителей и FK защищают создание/перенос задачи от конкурентного удаления объекта. При редких взаимных блокировках PostgreSQL отменит одну транзакцию; UI предлагает обновить данные и повторить действие. Автоматического повтора мутаций нет.

## Редактирование и назначение

Постановщик может редактировать содержание, объект и исполнителя в любом статусе, включая accepted. Статус и исторические метаданные сохраняются. Создание требует исполнителя. После переназначения RLS немедленно запрещает старому исполнителю последующие чтения и мутации, новому разрешает задачу и прежнюю историю. Имена участников отражают текущие имена профилей.

Редактирование содержания/переназначение не записывается в историю **статусов**. Полного аудита всех полей нет. Это осознанное ограничение предметной модели.

## Безвозвратное удаление

Удаление безвозвратное. Архивных экранов, полей мягкого удаления и функций восстановления нет.

Удаление доступно постановщику только через `delete_task` и `delete_object`. Функции проверяют роль, блокируют строку и сверяют версию. Объект разрешено удалить с любым количеством задач независимо от статусов. Удаляется состав задач на момент транзакции, включая добавленные после открытия подтверждения. Версия объекта защищает его собственные поля, а не является версией всех дочерних задач.

Историю удаляет FK ON DELETE CASCADE; при удалении объекта срабатывают оба уровня каскада. Триггер защиты истории:

1. Не допускает UPDATE.
2. Допускает INSERT только внутри вложенного триггера записи статуса. У API нет прав создавать свои триггеры или напрямую записывать таблицы.
3. Допускает DELETE только при вложенном вызове триггера и уже отсутствующей родительской задаче. Это соответствует FK-каскаду. Безусловный запрет DELETE заблокировал бы авторизованное удаление задачи и объекта.

Глубина триггеров сама по себе не является границей API-безопасности: её составляют отзыв write-привилегий, RLS, закрытые помощники и узкие авторизованные RPC. Отсутствие родителя дополнительно ограничивает DELETE. Не добавляйте обходные SECURITY DEFINER RPC без повторного анализа этих инвариантов. Администратор с полными правами находится за пределами ограничений обычных пользователей и технически может изменять схему.

В интерфейсе обязательны подтверждение и предупреждение о потере связанной истории. Восстановления в приложении нет. Резервное копирование платформы не заменяет архив CRM и не настраивалось.

## Сессии и интерфейс

Supabase SDK сохраняет Auth-сессию. Данные приложения хранятся только в памяти React и загружаются из базы. При выходе, смене пользователя или маршрута соответствующие экраны демонтируются; устаревшие ответы загрузчиков игнорируются. Нет localStorage-кэша объектов/задач. Auth-токен нужен для сессии; UI-роль не определяет разрешения базы.

Данные загружаются при открытии экрана, по кнопке обновления и после успешных мутаций. Возвращение фокуса на окно не запускает запросы и не скрывает список индикатором загрузки. При ошибке устаревшего действия нужно закрыть диалог, обновить данные и повторить действие. Уже показанную пользователю информацию отозвать невозможно; отзыв доступа действует на следующие запросы. Push-обновлений и постоянного опроса нет.

Сетевые запросы ограничены 30 секундами. При тайм-ауте пользователь получает указание обновить данные перед повтором: запрос записи мог успеть выполниться на сервере, даже если ответ не получен. Автоматические повторы мутаций не выполняются.

## Ограничения и незавершённые проверки

Приложение предназначено для небольшой одной компании, без мультитенантности. Списки читаются порциями с учётом серверного count, затем отображаются с клиентской пагинацией. При больших объёмах нужны серверная фильтрация и пагинация; несколько запросов чтения не составляют единый снимок базы. Времена показываются в часовом поясе браузера.

Профили/роли и Auth-пользователи управляются администратором. После административного изменения роли перезагрузите интерфейс; база применяет актуальную роль при запросах. Удаление связанных профилей/Auth-пользователей ограничено FK, чтобы не оставлять задачи и историю без участников.

Проверка типов, сборка и основные браузерные сценарии пройдены. Точный объём указан в `verification.md`; полный ручной чек-лист не следует считать пройденным автоматически. Доступы к демонстрационным аккаунтам передаются отдельно от исходников. Локальный `.env` исключён правилами `.gitignore`, в репозиторий включается только `.env.example` с заглушками.
