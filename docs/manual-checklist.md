# Ручная проверка

Это полный план проверки, **не отчёт об успешном прохождении всех пунктов**. Фактически выполненные проверки записаны в `verification.md`. Используйте отдельный тестовый проект и данные, которые можно безвозвратно удалить. Потребуются постановщик М и исполнители А/Б, отдельные браузерные профили или приватные окна. Для API используйте только публичный ключ и сессию проверяемого пользователя: service_role и SQL Editor администратора обходят ограничения и не подходят для проверки RLS.

## Установка и сессии

- [ ] Выполнить ещё не применённые миграции по порядку `001`, `002`, `003`, убедиться в завершении транзакций без ошибок. Уже выполненные файлы не повторять.
- [ ] Проверить FK: `tasks.object_id → objects.id` и `task_status_history.task_id → tasks.id` имеют DELETE CASCADE.
- [ ] Проверить, что `private` не раскрыта через Data API, публичная регистрация отключена, роли хранятся в `profiles`, браузеру выдан только публичный ключ.
- [ ] Самостоятельно установить зависимости, запустить проверку типов и сборку. Проверить запуск с конфигурацией и информационный экран без `.env`.
- [ ] Неверный пароль показывает понятную ошибку. Вход работает для всех пользователей, обновление страницы восстанавливает сессию. Пользователь без профиля видит сообщение и может выйти.
- [ ] После выхода/смены аккаунта, в том числе в другой вкладке, нет старых списков, форм и истории. Проверить выход во время медленной загрузки.
- [ ] На мобильной ширине 320–390 px формы, кнопки и история читаемы. Проверить клавиатуру, подписи полей и переход к содержимому.

## Постановщик и исполнители

- [ ] М создаёт и редактирует объекты, создаёт задачи, назначает А/Б. Пустые и пробельные названия, слишком длинные поля отклоняются UI и базой.
- [ ] А видит только свои задачи, Б — только свои, включая общий объект. Объект без задач текущего исполнителя ему не виден.
- [ ] А/Б не видят кнопок создания, редактирования содержания и удаления. Общий каталог профилей недоступен; имя автора и участников истории доступной задачи отображается.
- [ ] А выполняет `new → in_progress → in_review`, М принимает задачу. История содержит `NULL → new` и ровно одну запись каждого успешного перехода с реальным участником и временем.
- [ ] М возвращает другую задачу `in_review → revision` с комментарием; А начинает доработку и снова сдаёт на проверку. Комментарий виден в истории.
- [ ] М редактирует содержание/объект/исполнителя во всех статусах, включая accepted. Статус, автор, дата создания и существующая история не меняются.
- [ ] М переназначает задачу с А на Б. А теряет чтение и мутации по прежнему UUID, Б видит задачу с прежней историей. При переносе задачи между объектами видимость объектов меняется соответственно.

## Прямой API и запреты

Используйте Supabase SDK или REST как обычный пользователь. Сигнатуры RPC есть в `src/types/database.ts` и SQL. Для конкурентных действий сохраните исходную строку `updated_at` без преобразования даты. После запрещённого действия проверьте данные: отказ означает ошибку **или ноль видимых/изменённых строк при RLS**, а не обязательно HTTP 403.

- [ ] Без сессии нельзя читать таблицы или выполнять RPC.
- [ ] Под А запросить задачу Б, её историю и объект Б по известным UUID: select, фильтры и `task_identities` не возвращают чужих данных. Для недоступной/отсутствующей записи UI не показывает её поля.
- [ ] Под А и М попробовать прямые INSERT, UPDATE, DELETE, upsert в `objects`, `tasks`, `task_status_history`, а также запись в `profiles`. Всё отклонено, строки не меняются.
- [ ] Под А вызвать create/update/delete RPC объектов и задач: все отклонены.
- [ ] Под А попытаться повысить роль через `profiles` и Auth `user_metadata`: прав это не даёт. Назначение постановщика исполнителем отклоняется FK/RPC.
- [ ] В generic update RPC передать status, author_id, created_at, role: подходящей сигнатуры нет. Обычное редактирование эти поля не меняет.
- [ ] Под М вызвать worker-переходы `new → in_progress`, `in_progress → in_review`, `revision → in_progress`: запрещено. Под А вызвать приёмку/доработку: запрещено.
- [ ] Проверить `new → accepted`, `new → in_review`, обратные переходы, одинаковый статус, выход из accepted, несуществующий статус и NULL target. Статус и история не меняются.
- [ ] В revision передать NULL, пустую строку, пробелы, табы/переводы строк: всё отклонено. Непустой комментарий сохраняется.
- [ ] Для М и А попытаться вставить историю, изменить actor/time/comment/from/to, удалить одну запись или всю историю задачи, выполнить upsert истории: всё отклонено. Вспомогательные триггерные функции не доступны как RPC.
- [ ] Проверить ошибки сети, повтор загрузки, отсутствие записи и STALE_DATA. Ошибка не показывает сохранённые данные предыдущего аккаунта.

## Удаление и каскады — обязательная проверка

- [ ] В подтверждении задачи указаны безвозвратность и удаление всей истории. Отмена ничего не меняет.
- [ ] М удаляет задачу с несколькими переходами и комментарием. Задача и вся её история физически отсутствуют, остальные задачи сохранены. Повторить с accepted.
- [ ] Создать объект с задачами А/Б в разных статусах и историями; оставить независимый контрольный объект. Подтверждение объекта объясняет удаление всех задач и историй. Отмена ничего не меняет.
- [ ] М удаляет объект: объект, все задачи и истории физически отсутствуют; контрольный объект с его данными сохранён. `history_protection` **не блокирует** FK-каскад.
- [ ] М может удалить пустой объект. Объект с задачами не требует предварительного ручного удаления задач.
- [ ] А вызывает обе delete RPC и прямой DELETE из всех трёх таблиц: всё запрещено. М также не может напрямую удалить строки: нужен RPC.
- [ ] Открыть старые URL как М/А/Б, запросить старые UUID и сменить статус: записи недоступны, архива нет.
- [ ] Администратор через SQL Editor подтверждает физическое отсутствие строк: отсутствие данных при чтении работником не доказывает удаление. Прямое удаление существующей истории администраторским SQL без изменения защиты тоже отклоняется триггером.

## Конкурентные операции

- [ ] Два `change_task_status` с одинаковой версией: один успех, одна новая история, второй вызов отклонён.
- [ ] Два постановщика одновременно принимают/возвращают задачу с одной версией: одно решение, нет двойной истории.
- [ ] Открыть редактирование и изменить задачу в другой сессии: сохранение старой версии отклоняется. То же для объекта и его удаления.
- [ ] Переназначить задачу, пока прежний исполнитель меняет статус: если переназначение завершилось первым, старому исполнителю отказ. Если статус завершился первым, переназначение со старой версией требует обновления.
- [ ] Одновременно менять статус и удалять задачу: либо статус успевает и удаление со старой версией отклоняется, либо задача удалена и статус получает отказ; осиротевшей истории нет.
- [ ] Одновременно удалять объект и создавать/переносить в него задачу: после успешного удаления нет ссылок на объект и осиротевшей истории. Допустим отказ одной операции/повтор после взаимной блокировки. Добавленные до удаления задачи включаются в каскад.
- [ ] Повторить запрос после удаления: понятная ошибка, никакого восстановления или изменения других записей.
