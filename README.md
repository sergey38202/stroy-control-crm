# СтройКонтроль

Небольшая CRM строительной компании: **Объекты и задачи**. Постановщики создают объекты, назначают работы исполнителям и принимают результат. Исполнитель видит только свои задачи, начинает работу, отправляет её на проверку и устраняет замечания.

Проверка типов, production-сборка и основные браузерные сценарии пройдены. Выполненные проверки и ограничения описаны в [отчёте](docs/verification.md). Настройка Supabase и применение миграций выполняются администратором отдельно от приложения.

## Состав проекта

- `src/pages/` — вход, список объектов, объект, задача, список задач.
- `src/components/` — формы, подтверждения удаления и действия.
- `src/lib/` — Supabase, сессия, загрузка данных, обработка ошибок.
- `src/constants/routes.ts` — общий объект маршрутов и построение адресов карточек.
- `src/types/domain.ts` — строковые enum ролей и статусов, названия ролей.
- `src/types/database.ts` — вручную описанные типы таблиц и RPC.
- `supabase/migrations/202611040001_core.sql` — схема, RLS, жизненный цикл и RPC создания/редактирования.
- `supabase/migrations/202611040002_permanent_deletion.sql` — отдельная миграция каскадного удаления, RPC удаления и защита истории.
- `supabase/migrations/202611040003_stale_data_conflicts.sql` — явная ошибка HTTP 409 при устаревшей версии записи.
- `supabase/admin/provision_profiles.sql` — пример для администратора, не миграция и не RPC.
- `docs/` — решения, ручная проверка, объяснение руководителю.

## Зависимости

React 18, TypeScript 5.7 со строгим режимом, Vite 6, React Router 6, Ant Design 5, Supabase JS 2. Версии зафиксированы в `package.json` и `package-lock.json`; проверка типов и сборка выполнены с установленными зависимостями. Требуются Node.js 22 LTS и npm. Отдельный аудит уязвимостей зависимостей не проводился.

`package-lock.json` создан при установке зависимостей владельцем и включён в проект. Для установки зафиксированных версий используйте `npm ci`. При изменении зависимостей обновляйте lockfile вместе с `package.json` через `npm install`.

## Настройка вручную

1. В Supabase создайте проект. В настройках Authentication отключите публичную регистрацию: параметр **Allow new users to sign up / Enable sign ups** должен быть выключен. Название раздела может отличаться. Отсутствие экрана регистрации в CRM не заменяет отключение регистрации в Auth.
2. В SQL Editor от имени администратора последовательно выполните все три файла из `supabase/migrations/`: `001`, `002`, `003`. Каждый содержит транзакцию. Запишите, какие миграции применены. Если используете Supabase CLI, самостоятельно настройте его и применяйте эти же файлы по порядку.
3. В Data API используйте схему `public`. **Не добавляйте `private` в exposed schemas.** Схему `auth` также не раскрывайте. Realtime, Storage и отдельный backend не нужны.
4. Через административный интерфейс Authentication создайте три email/password учётные записи: постановщика и двух исполнителей. Подтвердите email административно или штатным способом. Пароли не записывайте в репозиторий.
5. Скопируйте UUID Auth-пользователей. В отдельной копии `supabase/admin/provision_profiles.sql` замените заглушки реальными UUID и выполните SQL как администратор. Роли не берутся из `user_metadata`.
6. Создайте `.env` по образцу `.env.example`. Укажите `VITE_SUPABASE_URL` и публичный publishable key в `VITE_SUPABASE_PUBLISHABLE_KEY`. Допустим старый публичный `anon` key. **Никогда не используйте service_role, secret key или пароль базы.** Всё с префиксом `VITE_` попадает в браузерную сборку.
7. В папке проекта выполните самостоятельно:

   ```sh
   npm ci
   npm run typecheck
   npm run dev
   ```

8. Войдите каждой учётной записью, подготовьте данные и пройдите [ручной чек-лист](docs/manual-checklist.md).

При отсутствии корректной конфигурации отображается инструкция по настройке. После изменения `.env` перезапустите Vite. В production переменные встраиваются во время сборки: при их изменении нужна новая сборка.

## Если база уже существует

Редактирование ранее выполненного SQL-файла **не меняет базу**. Если уже применён `001`, примените оставшиеся `002` и `003`; если выполнены `001` и `002`, примените только `202611040003_stale_data_conflicts.sql`. Повторять уже выполненные миграции не нужно. При свежей установке применяются все три файла.

Миграции предназначены для схемы этого проекта. Для другой существующей базы сначала сопоставьте таблицы, имена FK, RPC, триггеры и RLS и подготовьте адресную миграцию. Не выполняйте начальную миграцию поверх одноимённых таблиц. Старые RPC архивирования или записи истории не должны оставаться доступными. Этот проект не содержит полей мягкого удаления, архива или восстановления.

## Демонстрационные данные

Под постановщиком создайте 2–3 объекта: например «ЖК Северный», «Школа № 7», «Склад Восточный». Создайте задачи с описаниями и назначьте обоих исполнителей; на одном объекте обязательно назначьте задачи разным людям.

- Одну задачу оставьте новой.
- Под первым исполнителем начните вторую задачу: «В работе».
- Третью начните и отправьте на проверку.
- Под постановщиком верните её на доработку с замечанием.
- Ещё одну проведите через начало и проверку до приёмки.

История создаётся штатными переходами. Не вставляйте её вручную SQL-командами: она защищена триггером.

## Правила доступа и удаления

Все проверки находятся в PostgreSQL. Интерфейс только показывает доступные действия. Роли хранятся в защищённой таблице `profiles`; API-клиенты не могут менять профили. Исполнитель не получает общий справочник пользователей: отдельный RPC возвращает имена участников доступной задачи.

Таблицы доступны API только для чтения с RLS. Создание, редактирование, смена статуса и удаление выполняются через узкие RPC. Каждая мутация проверяет `auth.uid()` и роль. Изменение существующей записи блокирует строку и сверяет `updated_at`, переданный исходной строкой без потери точности PostgreSQL.

**Удаление безвозвратное и доступно только постановщикам:**

- Удаление задачи удаляет всю её историю статусов.
- Удаление объекта удаляет все его задачи в любых статусах и всю их историю.
- Связи `tasks.object_id → objects.id` и `task_status_history.task_id → tasks.id` имеют `ON DELETE CASCADE`.
- Отдельно вставить, изменить или удалить историю через API нельзя ни одной роли. Вставка идёт из триггера задачи; удаление разрешено только вложенному FK-каскаду после удаления родителя.
- Подтверждение объясняет полный объём удаления. Архива, корзины и восстановления нет. Состав удаляемых задач объекта определяется на момент транзакции.

## Сборка и размещение

Команды, которые вы запускаете самостоятельно:

```sh
npm run typecheck
npm run build
npm run preview
```

`build` проверяет TypeScript и создаёт `dist/`. `preview` нужен для локального просмотра результата. Для размещения достаточно статического хостинга с HTTPS. Приложение рассчитано на корень домена.

Для Vercel в корне проекта находится `vercel.json`: он задаёт Vite, установку через `npm ci`, сборку через `npm run build`, выходную папку `dist` и SPA fallback на `/index.html`. Файл необходимо закоммитить и отправить в репозиторий до публикации. Без него прямое открытие `/login`, `/objects/:id` или `/tasks/:id` может возвращать 404 хостинга. На другом хостинге настройте аналогичный fallback, сохранив раздачу существующих статических ресурсов.

В настройках Vercel добавьте `VITE_SUPABASE_URL` и `VITE_SUPABASE_PUBLISHABLE_KEY` из локальной конфигурации. `.env` в Git не отправляется. После изменения переменных нужна новая сборка. Настройте Site URL в Supabase Auth на опубликованный адрес приложения.

Дополнительные решения: [decisions.md](docs/decisions.md). Проверка безопасности: [manual-checklist.md](docs/manual-checklist.md).
